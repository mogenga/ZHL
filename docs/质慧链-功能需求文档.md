日期：2026-10-08
定位：业务逻辑实现与验收的唯一依据。业务边界已收敛，AI 职责边界已明确，复杂度保留项已标记。

---

# 第一篇 业务定义

## 1. 业务问题与目标

### 1.1 一句话定义

> 交付一批光伏组件之前，系统要能回答一个问题：**这批能不能放行？如果不能，哪些组件受影响、为什么、怎么复检、什么时候能恢复放行？**

### 1.2 真实痛点

| 痛点 | 现场表现 | 本系统的解法 |
| --- | --- | --- |
| 数据散落 | 纸质质检单、检验员个人 Excel、IV 设备 CSV 各存一处 | Agent 统一摄入为结构化检验记录，原始文件可回溯 |
| 判定不统一 | 同一标准，不同检验员判定口径不同 | 规则版本固化，判定由确定性引擎执行，公式可复算 |
| 不合格数据消失 | 入库校验失败直接拒绝保存，失败样本不留痕 | 校验失败即生成异常事件，保存失败证据 |
| 异常不闭环 | 不符合项只有「未完成/已完成」，无隔离、无复检、无放行关联 | 状态机强制隔离，复检通过才允许放行 |
| 归因靠人 | 翻台账、问现场、凭经验 | Agent 关联物料批号、设备、时间窗口，输出带证据的假设排序 |
| 放行凭感觉 | 说不清凭什么这批能放 | 放行断言逐条列出前提，缺一条即阻断 |

### 1.3 业务目标与可度量结果

| 目标 | 度量方式 |
| --- | --- |
| 检验数据自动结构化 | 抽取字段的人工修改差异率 |
| 判定口径统一可复算 | 每条判定都能回放规则版本 + 公式 + 输入 |
| 异常闭环不遗漏 | 异常关闭条件逐项校验，未满足即阻断 |
| 归因有证据支撑 | 用历史人工填写的根因回测 Top-1 / Top-3 命中率 |
| 报告自动生成 | 报告关键字段覆盖率 + 相对人工的耗时降幅 |

### 1.4 智能化职责边界

这是整个系统最关键的一条设计原则，是可信度的基础。

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| **AI / Agent** | 抽取数据、标注置信度、提示缺失项、跨批次关联证据、形成归因假设、生成报告草稿 | 修改判定公式结果、关闭异常、直接改变批次状态 |
| **规则引擎 + 状态机** | 计算 Pass/Fail、保存规则快照与原始证据、控制隔离复检放行 | 主观归因、补齐缺失规则 |
| **人工** | 确认低置信数据、确认根因与 CAPA、执行复检、批准放行或拒绝 | 修改已归档的原始检验值 |

一句话：**AI 给建议，规则做裁决，人工担责任。**

## 2. 业务范围界定

系统的目标是把交付前的批次质量判定组织为一个可执行、可验证的闭环。范围的取舍依据是评审关注度：**完成度与闭环合计占 45%，问题价值 20%，创新性 15%，技术深度与验证各 10%**。主链若无法被快速复述，闭环一项难以成立。

### 2.1 主链的收敛方式

把功能按「是否构成独立业务价值」合并为五段，而非按模块堆叠：

| 原本独立的功能点 | 归属段落 | 合并理由 |
| --- | --- | --- |
| 数据摄入 + 人工确认 | 第 1 段「数据入场」的内外两拍 | 摄入与确认是同一份数据的两个状态，不构成独立业务价值 |
| 单组件判定 + 批次抽样 | 第 2 段「规则判定」的前后两步 | 抽样本质是判定在批次层的展开 |
| 异常隔离 + CAPA + 复检 | 第 3 段归因、第 4 段复检放行 | 隔离不是一个动作，是状态机的分支结果 |
| 报告 + 归档 | 第 5 段「报告归档」 | 归档是报告生成的必然后续 |

### 2.2 必须修正的原始逻辑断点

以下五条来自平台现状，是「不改就讲不通」的地方，必须在需求中显式修正：

| 断点 | 原始行为 | 修正后 | 落实位置 |
| --- | --- | --- | --- |
| 异常无状态机 | 只有「未完成 / 已完成」两态 | 五态显式机，隔离/复检/放行各自独立 | [第 5.2 节](#s5-2) |
| 抽检结论可跨批次覆盖 | 唯一键缺 batchId | 唯一键为 batchId + inspectionType + ruleVersionId + sampleRound | [第 7 章](#ch7) |
| 校验失败数据消失 | 拒绝保存 | 保存失败证据并生成异常事件 | [第 8.1 节](#s8-1) |
| 规则配置无版本 | 改规则改写历史结论 | 每次判定保存 ruleVersion 与规则快照 | [第 6.4 节](#s6-4) |
| 异常涉及组件是文本 | modulesInvolved 自由文本 | 异常与 SN 建立关联关系，支持精确影响范围计算 | [第 3.4 节](#s3-4) |

不实现的内容见 [第 15 章](#ch15) 优先级表中的 P1 与 P2 说明。

## 3. 核心对象与最小数据模型

三个核心对象是：**批次、组件检验记录、异常事件**。支撑对象是规则版本与证据库。

### 3.1 规则版本 `QualityRuleVersion`

判定可复算的唯一依据。发布后不可修改。

| 字段 | 说明 | 约束 |
| --- | --- | --- |
| ruleVersionId | 规则版本 ID | 不可修改；变更必须发布新版本 |
| projectId / model | 项目、组件型号 | 必填 |
| nameplatePower | 铭牌功率 | 大于 0 |
| powerTolerance | 功率容差 | 非负百分比 |
| parameterStandards | 温度、Isc、Voc、Vm、FF 的标准值与容差 | 每项完整或禁用该项 |
| currentBands | Impp 电流分档上下限 | 区间不得重叠 |
| samplePlan | 检验类型、检验水平、AQL | 仅允许预置 ISO 值 |
| effectiveAt | 生效时间 | 不得晚于使用时间 |
| status | 草稿 / 已发布 / 已停用 | 仅已发布规则可判定 |

### 3.2 交付批次 `DeliveryBatch`

放行的最小业务对象。

| 字段 | 说明 |
| --- | --- |
| batchId / batchNo | 唯一批次标识 |
| projectId / model | 归属项目与型号 |
| plannedQuantity / actualQuantity | 计划数量与已纳入数量 |
| ruleVersionId | 本批次固定使用的规则版本 |
| status | 状态机状态 |
| releaseDecision | 放行 / 拒绝 / 未决 |
| releaseEvidenceId | 放行断言与报告的证据 ID |

### 3.3 组件检验记录 `ModuleInspection`

单个 SN 的检验事实。

| 字段 | 说明 |
| --- | --- |
| inspectionId | 记录 ID |
| batchId / SN | 必填；二者组合唯一 |
| sourceType | OCR_FORM / IV_CSV / MANUAL / SIMULATED_DEVICE |
| sourceFileId | 原始文件或模拟数据文件 |
| capturedAt | 检测时间 |
| pmax / temp / isc / voc / vm / im / ff | IV 参数 |
| appearanceResult | Pass / Fail |
| intakeStatus | 待确认 / 已确认 / 拒绝摄入 |
| decisionStatus | 待判定 / Pass / Fail / 规则缺失 |
| ruleSnapshot | 判定所用规则快照 |
| decisionEvidence | 每条规则项的输入、阈值、公式、结果 |

<a id="s3-4"></a>

### 3.4 异常事件 `QualityIncident`

阻断批次放行的最小治理对象。

| 字段 | 说明 |
| --- | --- |
| incidentId | 异常编号 |
| batchId | 必填；异常必须可阻断批次 |
| affectedSNs | 关联 SN 集合，不允许用自由文本替代 |
| triggerType | 规则失败 / 抽样失败 / 人工外观异常 / 数据一致性异常 |
| severity | 严重 / 主要 / 一般 |
| evidenceIds | 原始数据、判定快照、相关历史记录 |
| owner / dueAt | 处置责任人与时限 |
| containmentAction | 临时遏制措施，例如隔离对应托盘 |
| rootCauseHypotheses | AI 生成的证据化假设排序 |
| confirmedRootCause | 人工确认的根因 |
| correctiveAction | 纠正措施 |
| verificationId | 对应复检记录 |
| status | 异常状态机状态 |

### 3.5 复检 `Reinspection`

复检必须生成新记录，不覆盖初检。

字段：`reinspectionId、incidentId、SN、sourceFileId、检验参数、ruleVersionId、结果、执行人、时间、证据`。

**复检 Pass 不足以关闭异常**，还须验证临时措施、纠正措施与受影响范围。

### 3.6 证据库 `EvidenceStore`

支撑对象，保存源文件、判定快照、Agent 任务轨迹、报告版本。

每个条目记录：`evidenceId、类型、关联对象 ID、内容哈希、生成时间、生成者`。

# 第二篇 功能需求

## 4. 五段主链

### 4.0 主链总览

```text
① 数据入场 → ② 规则判定 → ③ AI 归因 → ④ 复检放行 → ⑤ 报告归档
                    │                              │
                    └── 失败 → 异常隔离 ←── 复检不过 ┘
```

一句话讲完：**Agent 把数据读进来，规则引擎算出合格不合格，Agent 找出为什么，规则引擎卡住放行，人签字，Agent 出报告。**

五段速查：

| 段 | 输入 | 输出 | 状态变化 | 失败去向 |
| --- | --- | --- | --- | --- |
| 1 数据入场 | 质检单、CSV、设备数据 | 带证据的检验记录 | 待入场 → 待判定 | 解析失败任务 |
| 2 规则判定 | 记录 + 规则版本 | 规则证据与 Pass/Fail | 待判定 → 待放行 / 已隔离 | 异常事件 |
| 3 AI 归因 | 异常 + 跨批次证据 | 假设排序 + 影响范围 | 已隔离 → 待处置 | 保持隔离 |
| 4 复检放行 | 新复检记录 + 措施确认 | 放行或拒绝决定 | 待复检 → 待放行 / 已拒绝 | 拒绝交付 |
| 5 报告归档 | 已放行或已隔离数据 | 版本化报告 | 已放行 / 已拒绝 → 已归档 | 不生成错误类型报告 |

### 4.1 第 1 段 数据入场

**输入**：质检单图片或 PDF、IV 设备 CSV，或用于联调的模拟设备数据。

**功能要求**

| 编号 | 要求 | 优先级 |
| --- | --- | --- |
| FR-1.1 | 支持至少一种设备数据格式的自动解析，建议优先 IV CSV | P0 |
| FR-1.2 | 支持纸质质检单图像的结构化抽取，可先以模拟文件补充 | P0 |
| FR-1.3 | 每个抽取字段携带置信度 | P0 |
| FR-1.4 | 校验类型、单位、SN 格式与批次归属 | P0 |
| FR-1.5 | 低置信度、缺字段、SN 重复、型号不匹配时生成待人工确认任务 | P0 |
| FR-1.6 | 人工确认后才写入正式检验记录 | P0 |
| FR-1.7 | 保存原始文件、抽取 JSON、模型版本、置信度、人工修改差异 | P0 |

**输出**：带证据的组件检验记录 + 完整抽取轨迹。

**失败去向**：解析失败 → 保留源文件与失败轨迹，创建重新提交任务；SN 冲突 → 触发数据一致性异常，阻断相关批次。

**闭环点**：AI 不能静默写入质量数据。每一个模型字段都有原始证据和人工责任人。

### 4.2 第 2 段 规则判定

**输入**：已确认检验记录 + 批次固定的规则版本。

**功能要求**

| 编号 | 要求 | 优先级 |
| --- | --- | --- |
| FR-2.1 | 按型号读取铭牌功率、参数标准、电流分档 | P0 |
| FR-2.2 | 功率范围与五项参数容差逐项判定 | P0 |
| FR-2.3 | Impp 电流分档判定 | P0 |
| FR-2.4 | 外观结论判定 | P0 |
| FR-2.5 | 逐项输出判定证据：输入值、阈值、公式、结果 | P0 |
| FR-2.6 | 批次层抽样判定，是否启用见 [第 7 章](#ch7)（待决事项 O-1） | 待决 |
| FR-2.7 | 任一必检项 Fail → 该组件 Fail，返回完整失败原因 | P0 |

**输出**：逐规则结果、总结果、规则快照、可复算公式。

**失败去向**：任一组件 Fail 或抽样 Fail → 批次进入异常隔离，创建异常事件。

**闭环点**：模型只解释「为什么失败」，不改变公式的计算结果。

### 4.3 第 3 段 AI 归因

**输入**：异常事件、受影响 SN、批次、物料批号、设备与时间窗口、历史检验记录。

**功能要求**

| 编号 | 要求 | 优先级 |
| --- | --- | --- |
| FR-3.1 | 关联 SN、批次、物料批号、设备、时间窗口、历史异常，构建关系视图 | P0 |
| FR-3.2 | 输出结构化 JSON 而非自由文本，含假设排序、置信度、证据引用 | P0 |
| FR-3.3 | 证据不足时输出缺失证据清单，不输出唯一根因 | P0 |
| FR-3.4 | 计算影响范围：同物料批号、同设备、同时间窗口的组件加入待调查集合 | P0 |
| FR-3.5 | 待调查集合不自动判为不合格 | P0 |
| FR-3.6 | 质量工程师可采纳、驳回或修改假设，被采纳内容才可写入确认根因 | P0 |
| FR-3.7 | 跨批次物料批号与时间窗口关联图 | P1 |

**输出**：带证据的归因假设排序 + 影响范围 + 缺失证据清单。

**失败去向**：证据不足 → 保持隔离，转人工补充证据。

**闭环点**：AI 的置信度是排序依据，不是放行依据。

### 4.4 第 4 段 复检与放行

**输入**：已处置异常 + 独立复检数据。

**功能要求**

| 编号 | 要求 | 优先级 |
| --- | --- | --- |
| FR-4.1 | 创建新的复检记录，引用原异常，不修改初检 | P0 |
| FR-4.2 | 重跑相同规则版本；规则变更时须显式选择原版本或新版本，不得混用 | P0 |
| FR-4.3 | 质量工程师确认临时措施与纠正措施已实施 | P0 |
| FR-4.4 | 执行放行断言，见 5.3 | P0 |
| FR-4.5 | 断言全通过才允许转为已放行 | P0 |
| FR-4.6 | 复检仍 Fail → 批次进入已拒绝 | P0 |
| FR-4.7 | 质量工程师可主动拒绝交付 | P0 |

**输出**：放行或拒绝决定、批准人、时间、断言结果、证据链。

**闭环点**：系统验证前提，质量工程师作最终签署，模型不越权。

### 4.5 第 5 段 报告归档

**功能要求**

| 编号 | 要求 | 优先级 |
| --- | --- | --- |
| FR-5.1 | 只可读取已确认的结构化数据生成报告 | P0 |
| FR-5.2 | 批次放行报告：批次信息、规则版本、抽样结论、检验统计、已关闭异常、放行断言、批准信息 | P0 |
| FR-5.3 | 质量处置报告：阻断原因、受影响 SN、异常证据、CAPA、复检状态、下一步待办 | P0 |
| FR-5.4 | 报告内嵌 Agent 任务轨迹 | P0 |
| FR-5.5 | 保存 reportVersion、sourceSnapshotId、agentTaskId、generatedAt；变更时生成新版本不覆盖 | P0 |
| FR-5.6 | 报告自然语言摘要与追问 | P1 |

**闭环点**：未放行批次只能生成处置报告，报告类型由状态强制约束。

## 5. 状态机与放行断言

### 5.1 批次状态机

```text
草稿 → 待入场 → 待判定
        │            ├── 判定通过 ──→ 待放行 → 已放行 → 已归档
        │            └── 任一失败 ──→ 已隔离 → 待处置 → 待复检
        │                                                  ├── 通过 → 待放行
        │                                                  └── 失败 → 已拒绝
        └── 人工拒绝 ─────────────────────────────────────→ 已拒绝
```

| 从 | 到 | 触发条件 | 输出 |
| --- | --- | --- | --- |
| 待入场 | 待判定 | 摄入完成且人工确认 | 抽取轨迹、原始文件、确认记录 |
| 待判定 | 待放行 | 全部组件通过且抽样 Pass | 判定快照、抽样结论 |
| 待判定 | 已隔离 | 任一组件 Fail、抽样 Fail、数据冲突、规则缺失 | 异常事件、隔离清单 |
| 已隔离 | 待处置 | 已指定责任人与时限 | CAPA 待办 |
| 待处置 | 待复检 | 临时措施与纠正措施已确认 | 复检任务 |
| 待复检 | 待放行 | 全部严重异常复检通过且措施有效 | 复检证据、断言结果 |
| 待放行 | 已放行 | 质量工程师批准且放行断言全成立 | 放行报告 |
| 任意非归档状态 | 已拒绝 | 复检失败或人工拒绝 | 处置报告 |

<a id="s5-2"></a>

### 5.2 异常状态机

```text
新建 → 已隔离 → 已指派 → 待复检 → 已关闭
                                  └──→ 已拒绝 / 已报废
```

**异常关闭必须同时满足五条，缺一即不得关闭，批次保持隔离：**

1. 已关联具体 SN，或明确声明整批受影响
2. 有原始判定证据
3. 有责任人、临时措施、确认根因、纠正措施
4. 有独立复检记录
5. 复检通过且质量工程师确认措施有效

### 5.3 放行断言

放行是一个可验证的布尔表达式，不是人工判断：

```text
batch.status == 待放行
AND latestSample.result == Pass        （启用抽样时）
AND openCriticalIncidentCount == 0
AND isolatedSNCount == 0
AND allRequiredEvidencePresent == true
AND allCriticalCAPAVerified == true
```

**断言在代码中实现为独立函数，每次放行尝试都执行并记录逐条结果。** 这是系统可信度的核心机制：当放行被拦截时，系统能逐条说明未满足的前提，而不是只给一个笼统的失败原因。

## 6. 规则判定详细逻辑

### 6.1 三重校验

判定严格按以下顺序执行，任一不通过即记录失败证据。

```text
① 基础校验：项目、SN、序号、等级、入库日期、六项电参数不可为空
② 功率范围校验：实测功率 ∈ [铭牌功率 ×(1 − 容差), 铭牌功率 ×(1 + 容差)]
③ 参数容差校验：温度、Isc、Voc、Vm、FF 五项各自与标准值比较
④ 电流分档校验：Impp 落在该型号对应的电流区间内
⑤ 外观校验：外观结论为 Pass
```

### 6.2 容差公式

```text
lower = 标准值 × (1 − 容差%)
upper = 标准值 × (1 + 容差%)
lower ≤ 实测值 ≤ upper        （闭区间）
```

**边界值语义**：闭区间，等于下限或上限均判 Pass。验收样例 2 专门验证这一点。

### 6.3 判定证据结构

每条规则项的判定必须输出可复算的四元组：

```json
{
  "rule": "powerRange",
  "input": {"nameplatePower": 550, "tolerance": 0.03, "actual": 533.5},
  "formula": "lower = nameplatePower × (1 - tolerance); upper = nameplatePower × (1 + tolerance)",
  "computed": {"lower": 533.5, "upper": 566.5},
  "result": "Pass"
}
```

<a id="s6-4"></a>

### 6.4 规则版本快照

每条检验记录保存判定时的完整规则快照。后续规则更新不得改写历史结论——这是「判定可复算」的硬保证，也是本系统区别于普通质检软件的关键点。

## 7. ISO 抽样：三个待决方案

抽样逻辑复杂度中等，收益明确（体现批量检验业务特征），但会增加开发量与状态复杂度。三个方案都写入文档，**待定后再锁定实现范围**。

### 方案一 降为插件级（推荐）

抽样作为规则引擎插件保留，在第 2 段判定环节内部调用，不出现在主链叙述中。

- 实现范围：预置一张 ISO 抽样表，参数限定检验类型 + 检验水平 + AQL + 批量，返回 n / AC / RE
- 状态机：零新增状态
- 开发量：小
- 业务完整性：中。n/AC/RE 是批量抽样概念，保留后可完整表达「批量检验」语义
- 风险：低

### 方案二 移出主链

抽样完全砍掉，批次合格 = 全部组件 Pass。

- 实现范围：无
- 开发量：零
- 业务完整性：低。主链最短，但丢失批量抽检特征
- 风险：低，但会脱离「批量检验」的真实业务语义

### 方案三 升为独立环节

抽样作为独立步骤，配样本清单界面与抽样轮次管理。

- 实现范围：样本冻结、抽样轮次、样本清单 UI、唯一键约束、多轮复检
- 状态机：新增「待抽样」状态
- 开发量：大
- 业务完整性：高。可完整表达「本轮抽了哪 8 块、为什么是这 8 块」
- 风险：中。轮次与样本一致性逻辑易出缺陷

### 三个方案共同遵循的约束

无论选哪个方案，以下约束都必须满足：

| 约束 | 说明 |
| --- | --- |
| AQL 必须取标准值 | 不允许自定义任意 AQL |
| 样本必须冻结 | 抽检结论基于固定样本清单，不允许从当前列表重新随机选择 |
| 结论唯一键 | batchId + inspectionType + ruleVersionId + sampleRound，历史只读 |
| 表项缺失即阻断 | ISO 表查不到对应项 → 判定为规则异常，禁止按默认值放行 |

**建议**：优先按方案一实现。若 [第 13 章](#ch13) 的 FDE 资产沉淀进展顺利且时间充裕，再升级到方案三。方案二不推荐。最终决策见 [第 16 章待决事项 O-1](#o1)。

## 8. 异常闭环与 CAPA

<a id="s8-1"></a>

### 8.1 触发条件

以下任一情况自动创建异常事件：

- 组件确定性判定 Fail
- 抽样判定 Fail（启用时）
- SN 重复或跨批次冲突
- 型号无已发布规则
- 人工判定外观异常

### 8.2 隔离动作

1. 创建异常事件，保存触发规则与全部证据
2. 组件级异常 → 隔离对应 SN；批次级异常 → 隔离整个批次
3. 在批次上写入阻断原因，停止放行报告生成
4. 计算影响范围，生成待调查集合
5. 指定责任人与处置时限

**关键区别**：异常不只是列表中的一行数据，它实际阻断批次状态转移。这是「闭环」二字的具体落点。

### 8.3 CAPA 内容要求

| 字段 | 要求 |
| --- | --- |
| 临时遏制措施 | 必填，如隔离对应托盘、暂停该物料批号投料 |
| 确认根本原因 | 必填，必须来自人工采纳的 AI 假设或人工填写 |
| 纠正措施 | 必填，须可验证 |
| 责任人与时限 | 必填 |

### 8.4 与平台现状的差异

现有系统的符合项记录只有「未完成 / 已完成」两态，无隔离、无复检、无放行关联。本章定义的五态机是必须修正的核心断点，也是本项目「改造现有平台」的最小充分证明。

# 第三篇 AI 融入设计

## 9. AI 落点总览与职责边界

### 9.1 AI 落在哪里

系统共三处 AI 落点，覆盖「读懂非结构化输入」到「输出可审计结论」的完整能力面：

| AI 落点 | 解决的问题 | 复杂度 | 优先级 |
| --- | --- | --- | --- |
| 结构化抽取与置信度 | 非结构化输入 → 可用数据 | 中 | P0 |
| 证据化归因假设 | 跨批次关联与假设生成 | 高 | P0 |
| 规则与阈值推荐 | 经验参数 → 数据驱动建议 | 高 | P1 |

### 9.2 为什么这三处

| 不该放 AI 的地方 | 原因 |
| --- | --- |
| Pass/Fail 计算 | 质量判定必须确定性、可复算、可审计 |
| 状态机流转 | 治理逻辑必须可预测，不能有概率性 |
| 放行断言 | 这是安全边界，必须是硬编码布尔表达式 |
| 报告数据汇总 | 数值必须来自结构化事实，不能由模型复述 |

**判据**：AI 处理「需要判断力的非确定性环节」，规则引擎处理「必须确定的计算与治理」。这条边界是本系统可信度的基础。

### 9.3 每次 Agent 任务必须保存的轨迹

```text
taskId、输入引用、Skill 名称、调用的 Plugin、工具参数摘要、
模型版本、结构化输出、验证结果、失败原因、人工操作、开始与结束时间
```

轨迹的完整性决定了决策过程可复演：模型提出了什么、系统调用了什么、哪条规则通过或失败、谁作出最终决定。

### 9.4 Skill 与 Plugin 边界

| 组件 | 类型 | 职责 | 不负责 |
| --- | --- | --- | --- |
| Inspection Intake Skill | Skill | 识别文件、补齐字段、提出确认任务 | 直接放行 |
| Quality Decision Skill | Skill | 编排并解释规则计算 | 修改规则值 |
| Trace-and-CAPA Skill | Skill | 汇集证据、提出归因假设与建议 | 确认根因、关闭异常 |
| Rule Advisory Skill | Skill | 基于历史数据推荐规则参数 | 直接发布规则 |
| Report Delivery Skill | Skill | 汇总事实、生成报告草稿 | 编造数据、改变批次状态 |
| Inspection Data Plugin | Plugin | 读取 OCR / CSV / 模拟设备数据 | 业务判定 |
| Rule Engine Plugin | Plugin | 确定性公式计算与规则快照 | 模型推理 |
| Sampling Plugin | Plugin | ISO 表查询、样本冻结、统计 | 任意生成 AQL |
| Traceability Plugin | Plugin | SN—批次—物料—设备关系查询 | 主观归因 |
| Evidence Store Plugin | Plugin | 保存源文件、证据、轨迹 | 决定放行 |

## 10. AI 点一：结构化抽取与置信度

### 10.1 功能描述

读取质检单图片、PDF 或设备 CSV，抽取 SN、型号、检测时间、IV 参数等字段，为每个字段输出置信度，低置信字段自动进入人工确认队列。

### 10.2 输出结构

```json
{
  "batchNo": "B-2026-06",
  "fields": [
    {"name": "sn", "value": "SN88213", "confidence": 0.98, "source": "csv:row2"},
    {"name": "pmax", "value": 534.2, "confidence": 0.99, "source": "csv:row2"},
    {"name": "temp", "value": null, "confidence": 0.0, "source": null,
     "issue": "missing_in_source"}
  ],
  "schemaIssues": ["temp_missing"],
  "needsHumanReview": ["temp"]
}
```

<a id="s10-3"></a>

### 10.3 量化验证

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 字段级准确率 | 抽取正确字段数 / 总字段数 | ≥ 95% |
| 自动通过率 | 高置信无需人工核对的比例 | ≥ 80% |
| 人工修改差异率 | 人工改动字段数 / 人工核对字段数 | 越低越好 |
| 漏检率 | 应识别异常却漏识的比例 | 越低越好 |

### 10.4 验收流程

上传一张历史质检单 → 展示抽取结果 → 展开字段置信度 → 只核对红黄字段 → 确认入库 → 展示报告里的原始文件与修改差异对照。

---

## 11. AI 点二：证据化归因假设

### 11.1 功能描述

对已隔离的批次，跨批次关联 SN、物料批号、设备、时间窗口与历史异常记录，输出带证据引用与置信度的假设排序。

### 11.2 输出结构

```json
{
  "hypotheses": [
    {
      "rank": 1,
      "cause": "物料批号 M-2026-01 的 Impp 分布整体偏低",
      "confidence": 0.78,
      "evidence": ["inspection:IM-102", "batch:B-06", "materialLot:M-2026-01"],
      "recommendedAction": "隔离同物料批号待检组件并扩大复检样本"
    },
    {
      "rank": 2,
      "cause": "IV 测试仪 V-03 在该时间窗口存在校准漂移记录",
      "confidence": 0.41,
      "evidence": ["device:V-03", "calibration:2026-05-12"],
      "recommendedAction": "调取该设备校准记录复核"
    }
  ],
  "missingEvidence": ["设备校准记录", "该时段原材料入库检验单"]
}
```

### 11.3 强制约束

| 约束 | 说明 |
| --- | --- |
| 必须结构化输出 | 不接受自由文本结论 |
| 证据必须可点击 | 每条 evidenceId 能跳转到对应原始记录 |
| 证据不足不输出唯一根因 | 必须同时给出 missingEvidence |
| 待调查不等于不合格 | 影响范围内的组件只标记，不判废 |
| 人工有最终决定权 | 采纳、驳回、修改三选一，被采纳才可写入确认根因 |

<a id="s11-4"></a>

### 11.4 量化验证

用历史人工填写的根因做回测：

| 指标 | 定义 |
| --- | --- |
| 归因 Top-1 命中率 | 排序第一的假设与人工根因一致的比例 |
| 归因 Top-3 命中率 | 前三中包含人工根因的比例 |
| 证据可回溯率 | 假设引用的证据能定位到原始记录的比例 |
| 幻觉率 | 输出无法被任何证据支撑的结论的比例 |

### 11.5 验收流程

点开隔离批次 → 展示 Agent 关联到的 5 条证据 → 展开假设排序 → 采纳第一条 → 生成 CAPA 待办 → 展示影响范围的 17 块组件 → 发起扩大复检。

## 12. AI 点三：规则与阈值推荐

### 12.1 功能描述

基于历史合格批次数据，为新型号推荐功率容差、参数容差、电流分档与抽样等级的建议值，输出推导依据，交质量工程师确认后固化为规则版本。

### 12.2 关键约束

这一项的前提是**必须有历史业务数据**。若历史数据不可得，本项降级为 P1 或不做，不得用编造数据代替真实样本推导。

| 约束 | 说明 |
| --- | --- |
| 必须给出推导依据 | 每个建议值附样本量、分布区间、覆盖比例 |
| 只能建议不能发布 | 发布规则版本必须人工确认 |
| 不修改已发布规则 | 建议只对新版本生效，历史结论不受影响 |
| 覆盖比例必须明示 | 例如「该容差覆盖历史合格数据的 99.2%，异常样本中 96% 被拦截」 |

### 12.3 输出结构

```json
{
  "model": "JH-550W",
  "recommendations": [
    {
      "field": "powerTolerance",
      "currentValue": 0.03,
      "suggestedValue": 0.025,
      "basis": {
        "sampleSize": 1840,
        "coverageOfGoodSamples": 0.992,
        "rejectionOfBadSamples": 0.961,
        "note": "收紧至 2.5% 后历史异常样本拦截率由 89% 升至 96%"
      }
    }
  ]
}
```

### 12.4 风险提示

本项是三处 AI 落点中前提最硬的一处。若历史数据不足或不可得，**宁可不做，也不要用模拟数据冒充真实推导**——推导依据必须可追溯到真实样本。

# 第四篇 交付与验收

<a id="ch14"></a>

## 14. 四组验收样例

每组样例给出输入、预期状态序列、断言验证点。这是「闭环 20% + 验证 10%」的直接证据。

### 样例一 正常放行

**输入**：一个批次 10 个组件，全部 IV 参数在规则范围内，外观 Pass。

**预期状态序列**

```text
待入场 → 待判定 → 待放行 → 已放行 → 已归档
```

**断言验证点**

- 报告中的样本清单与判定结论一致
- 规则版本号与 snapshot 可逐项回查
- 每条判定都能复现计算过程
- 放行断言逐条为 true

### 样例二 边界值

**输入**：一个组件 Pmax 恰好等于功率下限，其他项目合格。

**预期结果**：判定为 Pass。

**断言验证点**

- 展示闭区间公式：`lower = 550 × (1 − 0.03) = 533.5`，实测 533.5 判 Pass
- 证明判定来自规则引擎，而非模型主观判断
- 对照组：533.4 应判 Fail

### 样例三 异常隔离与复检

**输入**：一个组件 Impp 超出电流分档；历史中同物料批号有同类 Impp 偏低记录。

**预期状态序列**

```text
待入场 → 待判定 → 已隔离 → 待处置 → 待复检 → 待放行 → 已放行
```

**断言验证点**

- 未完成复检时尝试放行，必须被断言阻断
- AI 输出带证据的「物料批号相关」假设，引用可跳转
- 复检前只能生成质量处置报告，不能生成放行报告
- 复检通过且异常关闭后，才允许放行
- 复检生成新记录，初检记录未被修改

### 样例四 数据一致性异常

**输入**：同一 SN 再次上传并指向另一批次。

**预期结果**：不覆盖旧记录，创建数据一致性异常，两个批次均不可放行。

**断言验证点**

- 原始记录完整保留
- 异常关联两个批次
- 两个批次的放行按钮均被断言拦截
- 证明系统对错误数据有处理闭环，而非只处理理想输入

## 15. 复杂度保留清单与优先级

下表同时给出优先级与实现方式。P0 必须实现并通过验收样例验证，P1 为增强项，P2 不做。

| 编号 | 保留逻辑 | 复杂度来源 | 优先级 | 实现方式 |
| --- | --- | --- | --- | --- |
| C-1 | 规则版本快照与判定可复算 | 版本管理与历史一致性 | P0 | 规则引擎插件 |
| C-2 | 放行断言机制 | 多前提布尔校验与阻断 | P0 | 独立断言函数 |
| C-3 | 异常五态状态机 | 状态与数据一致性的维护 | P0 | 状态机模块 |
| C-4 | 跨批次归因关联 | 多维关系图查询 | P0 | Traceability Plugin + Agent |
| C-5 | 证据化假设输出 | 结构化 JSON 约束与引用 | P0 | Skill 提示词工程 |
| C-6 | 样本冻结与唯一键 | 一致性与覆盖风险 | P0 | Sampling Plugin |
| C-7 | 字段级置信度与人工差异 | 校准与展示 | P0 | Intake Skill |
| C-8 | 规则阈值推荐 | 统计推导与依据呈现 | P1（视数据可得性，见 [O-2](#o2)） | Advisory Skill |
| C-9 | 影响范围计算 | 同批号同设备同时窗的关联 | P1 | Traceability Plugin |

### 15.1 P0 的完成标准

P0 不是「做了」而是「验证过」。以下四条链路必须可复现：

- 一条完整的放行链路
- 一条完整的异常隔离到复检放行链路
- 一次被放行断言阻断的验证场景
- 四组验收样例与完整任务轨迹（[第 14 章](#ch14)）

其中 AI 落点要求三处中至少实现两处：结构化抽取与证据化归因为必选。
