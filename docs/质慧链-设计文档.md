## 1. 系统概览

平台是一个 Python 单体服务：FastAPI 提供 REST API 并托管内置前端页面，PostgreSQL 保存业务数据、证据索引与操作轨迹，SQLAlchemy 负责持久化，LangGraph 承载数据入场、抽取、人工确认、判定、抽样与状态推进的主工作流。

```text
        质量工程师 ──► 内置工作台页面（app/static）──┐
                                                    ├─► FastAPI 接入层（app/api）
        外部客户端 ────────────────────────────────┘      │
                                                           ▼
                                                  LangGraph 主工作流
                                                  intake → extract
                                                  → human_confirm
                                                  → judge → sample
                                                  → advance
                                                           │
                        ┌──────────────────────────────────┤
                        ▼                                  ▼
                   Skill 层                          领域层（纯函数）
                 （app/skills）                判定引擎 / 抽样 / 状态机
                        │                        / 放行断言
                        ▼                                  │
                   Plugin 层                               │
                （app/plugins）                             │
             证据存储 / 归因证据过滤                        │
             抽样持久化 / 报告渲染 / 轨迹存储               │
                        │                                  │
                        └──────────────┬───────────────────┘
                                       ▼
                        PostgreSQL（业务数据 / 证据索引 / 操作轨迹）
                             + 原始证据文件存储
```

三层调用方向是固定的：**接入层只做校验和建会话，不含业务判断；工作流层只做编排，不含计算；所有计算下沉到领域层**。

### 1.1 五条核心设计原则

这五条决定了后面所有的技术选择，理解它们比理解代码更重要：

| 原则         | 含义                 | 带来的约束             |
| ---------- | ------------------ | ----------------- |
| **判定可复算**  | 每次判定都保存当时的规则快照     | 后续规则变更不会改写历史结论    |
| **状态流转确定** | 状态转移是纯函数           | 模型无法参与状态改写，只能提供建议 |
| **证据可回溯**  | 任何结论都能追到原始文件       | 证据只追加，不允许修改或删除    |
| **过程可复演**  | 每个任务输入、调用、输出、验证全留痕 | 轨迹表与业务写入同事务提交     |
| **约束下沉**   | 唯一性、完整性由数据库声明式保证   | 不依赖应用层校验兜底        |

### 1.2 AI 的角色边界

这是整套设计里最关键的一条：

| 角色             | 负责                                     | 不负责                  |
| -------------- | -------------------------------------- | -------------------- |
| **AI / Agent** | 抽取数据、标注置信度、提示缺失项、跨批次关联证据、形成归因假设、生成报告草稿 | 修改判定结果、关闭异常、直接改变批次状态 |
| **规则引擎 + 状态机** | 计算 Pass/Fail、保存规则快照与证据、控制隔离复检放行        | 主观归因、补齐缺失规则          |
| **人工**         | 确认低置信数据、确认根因与 CAPA、执行复检、批准放行或拒绝        | 修改已归档的原始检验值          |

一句话：**AI 给建议，规则做裁决，人工担责任。** 放行是质量闸门，不能交给一个会"猜"的模型决定。

## 2. 分层与模块职责

| 层        | 目录                       | 职责                                |
| -------- | ------------------------ | --------------------------------- |
| 接入层      | `app/api`                | 接收请求、UUID 与请求数据校验、创建请求级会话、返回结构化错误 |
| 工作流层     | `app/workflow`           | 编排主链与状态推进，管理人工确认中断与恢复             |
| Skill 层  | `app/skills`             | 抽取、批量判定、报告生成等业务语义                 |
| Plugin 层 | `app/plugins`            | 证据存储、归因证据过滤、抽样持久化、报告渲染、轨迹存储       |
| 领域层      | `app/domain`             | 不读数据库、不取当前时间、不调用模型的判定、抽样、状态机与放行断言 |
| 数据层      | `app/infra`、`migrations` | ORM 定义、仓库、PostgreSQL 迁移与约束        |
| 展示层      | `app/static`             | 无构建链的原生 HTML + JavaScript 工作台页面   |

**领域层是整套设计的支点**：它只接收调用方传入的数据视图，不依赖 SQLAlchemy、LangGraph 或模型客户端。这让边界值、非法状态、断言分支可以脱离数据库独立测试——`app/domain/sampling.py` 里连随机数都由调用方传入种子，不自己取随机源。

## 3. 一次检验的完整执行链路

```text
  ① 数据入场 ──录入完成──► ② 规则判定
                            │
              全部通过 ─────┼───── 任一失败 ──► ③ AI 归因
                 │                              │
                 │                          开启归因
                 │                              ▼
                 │                         异常隔离 ◄────┐
                 │                              │         │
                 │                         复检通过    复检不过
                 │                              │         │
                 │                              └───► ④ 复检放行
                 │                                        │
                 │                              放行通过 ──┤
                 │                                        ▼
                 └── 隔离批次被拒绝 ──────────────► ⑤ 报告归档
```

只有两条路能走到第 ⑤ 段：**全部判定通过后放行**，或**隔离批次被人工拒绝**。任何一条判定失败都会把批次推进异常回路，必须先关闭异常或完成复检才能回到放行通道。

### 3.1 第 1 段：数据入场

```text
  质检单 / IV设备 CSV
          ↓
  POST /api/intake
          ↓
  LangGraph 主图启动
          ↓
  写 inspection 行（status=pending）
          ↓
  ┌───────────────────────┐
  │ 抽取置信度是否足够？   │
  └───────────┬───────────┘
        是 │         │ 否
           ▼         ▼
    自动确认   中断在 human_confirm
                  ↓
        POST /api/intake/{task_id}/confirm
        （人工逐条确认或拒绝）
           │
           └──────► 两者汇合
                      ↓
          批次推进到 pending_judge
```

**关键设计**：低置信度时主图**中断**而不是猜。人工确认后从checkpointer 恢复继续。这保证 AI 抽错的字段一定有人工确认过。

**跨批次 SN 冲突**：同一 SN 已在另一批次存在时返回 `cross_batch_sn_conflict`，并列出冲突的 SN 清单，由人工决定是否放行。

### 3.2 第 2 段：规则判定与抽样

```text
  inspection 行 + rule_version 规则快照
          ↓
  逐 SN 计算 Pmax / Voc / Isc / Vm / Im / FF
          ↓
  与参数标准比对
    upper = 标准 × (1 + 偏差)
    lower = 标准 × (1 − 偏差)
          ↓
  电流分档 Impp → bin1 / bin2 / ...
          ↓
  ┌───────────────────────┐
  │      三重校验          │
  │ 1. 基础校验：逐 SN 比对是否超差│
  │ 2. 抽样校验：按抽样计划接收/拒收 │
  │ 3. 漏检过滤：检出力不小于同位号   │
  └───────────┬───────────┘
        是 │         │ 任一失败
           ▼         ▼
  pending_release   发起异常事件 → isolated
```

**判定的三重校验**（`state.html` 有完整对照表）：

| 校验   | 含义              |
| ---- | --------------- |
| 基础校验 | 逐 SN 比对参数标准是否超差 |
| 抽样校验 | 按抽样计划的接收/拒收数判定  |
| 漏检过滤 | 逐项检出力不小于同位号方案   |

`lower ≤ 实测值 ≤ upper` 才算 Pass；`lower =标准值 ×(1 − 偏差)`。

### 3.3 第 3 段：AI 归因

判定失败后，系统开启归因分析：

```text
  异常事件 + 跨批次证据
          ↓
  EvidenceFilter
  按物料批号 / 设备 / 时间窗口过滤
          ↓
  TraceStore
  读取历史任务轨迹
          ↓
  LLM 生成
  假设排序 + 影响范围
          ↓
  写入 quality_incidents（假设 + 证据引用）
```

**归因假设必须带证据引用**——没有证据支撑的假设不写库。这是防止模型幻觉的关键：AI 说"可能是这批物料有问题"，必须能指出是哪几条记录支持这个说法。

### 3.4 第 4 段：复检与放行

异常闭环（指派 → CAPA → 复检 → 关闭）与放行是两条独立推进的路径：

```text
异常侧：new → isolated → assigned → pending_recheck → closed
                                          └──→ rejected / scrapped

放行侧：pending_judge → pending_release → released
              ↓任一失败
          isolated → disposing → pending_recheck → pending_release
```

**放行七项断言**（`release.py`），全部通过才写放行决定：

| # | 断言                           |
| - | ---------------------------- |
| 1 | 批次状态 == `pending_release`    |
| 2 | 最新抽样结果 == Pass               |
| 3 | `operational_call_rate` == 0 |
| 4 | 隔离批次数 == 0                   |
| 5 | 全部必需 CAPA 已提交                |
| 6 | 全部隔离处置者已验证                   |
| 7 | 每个未关闭异常都有明确结论                |

任一条不过 → **阻断**，返回未过项清单并可重试。这七条是 `AND` 关系，**不允许任何一条为 false**（"不是系统判定的 false"）。

### 3.5 第 5 段：报告归档

```text
已放行 / 已拒绝的批次
        ↓
  POST /api/batches/{id}/report
        ↓
  按批次 + 类型 + 版本保存
        ↓
  Markdown + 结构化 JSON + 快照引用
```

已拒绝的批次只能生成 incident 类型报告（放行报告无意义），类型不匹配返回 409。

## 4. 核心机制设计

### 4.1 LangGraph 主工作流

```text
intake → extract → human_confirm(可中断) → judge → sample → advance
```

- `human_confirm` 是**中断点**：置信度不足时流程挂起，等人工确认后从 checkpointer 恢复
- 其余节点是普通转换，图结构固定不可变
- 状态推进由`domain/transition` 纯函数执行，不在图里写业务判断

### 4.2 Skill 与 Plugin 的划分

| 类型         | 职责                        | 例子                                            |
| ---------- | ------------------------- | --------------------------------------------- |
| **Skill**  | 业务语义，编排多个 Plugin 完成一个业务动作 | `intake` Skill：调用 LLM 抽取 Plugin + 证据存储 Plugin |
| **Plugin** | 单一技术能力，无业务语义              | `evidence` Plugin：写文件、算哈希、登记 evidence 表       |

这样划分的收益：Skill 可以复用 Plugin，Plugin 可以独立测试。业务逻辑集中在 Skill，技术细节下沉到 Plugin。

### 4.3 事务边界

```text
一次请求 = 一个事务
├── 业务写入（批次/异常/复检/报告）
└── 轨迹写入（agent_task_traces）
```

业务数据与轨迹记录**同事务提交**——不会出现"业务成功但轨迹丢了"的情况，反之亦然。回滚时两者一起回滚。

### 4.4 证据链

```text
原始文件（本地只追加）
    ↓ 哈希 + 路径 + 引用对象
evidence 表
    ↓ 关联
inspection / incident / report
```

模型只保存结构化摘要 + 证据引用 ID，不复制原始内容。这样保证原始文件不可被篡改，且任何结论都能顺着引用链回溯到源文件。

## 5. 状态机

### 5.1 批次状态

```text
draft → pending_intake → pending_judge
pending_judge → pending_release | isolated
isolated → disposing → pending_recheck
pending_recheck → pending_release | rejected
pending_release → released
released | rejected → archived
```

| 转移                                  | 前置条件           |
| ----------------------------------- | -------------- |
| `draft → pending_intake`            | 无              |
| `pending_intake → pending_judge`    | 无              |
| `pending_judge → pending_release`   | 全部组件通过且抽样通过    |
| `pending_judge → isolated`          | 任一失败、数据冲突或规则缺失 |
| `isolated → disposing`              | 已设置责任人与时限      |
| `disposing → pending_recheck`       | 措施已确认          |
| `pending_recheck → pending_release` | 复检通过且措施有效      |
| `pending_recheck → rejected`        | 复检失败路径         |
| `pending_release → released`        | 七项断言通过且人工批准    |
| 非归档状态 → `rejected`                  | 人工拒绝           |
| `released/rejected → archived`      | 无              |

状态转移表在领域层以**数据驱动**方式实现，非法状态或缺少前置条件统一返回拒绝原因。

### 5.2 异常状态

```text
new → isolated → assigned → pending_recheck → closed
                                    ├──→ rejected
assigned → scrapped
```

异常关闭除状态机边外，还需通过 `close_incident` 硬性校验：**责任人、根因与纠正措施、复检记录、复检通过、CAPA 已验证**五项必须同时具备。

### 5.3 归档终态守卫（D8）

批次进入 `archived` 后，所有写接口返回 409。守卫以全局依赖形式挂在写路由上，防止归档后被继续修改——归档意味着这份数据已成为历史事实，不能再动。

## 6. 数据设计与完整性控制

PostgreSQL 初始迁移建立规则、批次、检验、异常、复检、抽样、证据、轨迹和报告共**十二个主要表**。

| 表                       | 用途                          |
| ----------------------- | --------------------------- |
| `quality_rule_versions` | 规则版本、参数标准、电流档位和抽样计划         |
| `delivery_batches`      | 批次主数据、当前状态、放行决定与放行证据        |
| `module_inspections`    | 组件原始检验值、摄入状态、判定状态、规则快照与判定证据 |
| `quality_incidents`     | 异常触发、严重级别、责任人、CAPA、归因假设与状态  |
| `incident_sn_links`     | 异常与受影响检验记录的多对多关联            |
| `reinspections`         | 保留初检不覆盖的复检记录与复检范围           |
| `samples`               | 冻结后的抽样 SN 与随机种子             |
| `sample_conclusions`    | 抽样轮次、样本量、接收数、拒收数与结论         |
| `iso_sampling_table`    | ISO 抽样查询表                   |
| `evidence`              | 证据索引、文件哈希、路径、对象引用与生成信息      |
| `agent_task_traces`     | Skill 与 Plugin 的结构化任务轨迹     |
| `reports`               | 报告类型、版本、Markdown、JSON 与快照引用 |

### 6.1 关键完整性约束

| 约束                          | 实现方式         |
| --------------------------- | ------------ |
| 批次号唯一                       | 唯一索引         |
| 规则版本在「项目+型号+版本号」唯一          | 复合唯一约束       |
| 组件 SN 在单批次内唯一               | 唯一约束         |
| **同一 SN 不可跨批次重复进入**         | **范围排他约束**   |
| 抽样明细与结论在「批次+检验类型+规则版本+轮次」唯一 | 复合唯一约束       |
| 发布后的规则版本不可修改                | **数据库触发器保护** |
| 原始检验值与证据不可改写/删除             | 权限控制 + 追加式设计 |
| 报告按「批次+类型+版本」保存，历史不覆盖       | 复合唯一约束       |

**约束下沉**原则的体现：跨批次 SN 冲突、发布规则不可改这些约束由数据库声明，应用层即使漏了判断也进不去。

ORM 模型兼容 SQLite 内存库，因此 API 与领域测试无需启动 PostgreSQL；PostgreSQL 特有的触发器、排他约束、权限控制**以迁移 DDL 为最终权威**。

## 7. 接口设计

生产入口 `app.main:app`（`create_unified_app`），同时装配 Phase A（批次、摄入）与 Phase B（异常、复检、放行、报告、轨迹、静态页）。

| 范围 | 接口                                       | 说明                             |
| -- | ---------------------------------------- | ------------------------------ |
| 批次 | `POST /api/batches`                      | 创建批次并进入待入场                     |
| 批次 | `GET /api/batches`                       | 批次列表（前端工作台主数据源），支持 `status` 过滤 |
| 批次 | `GET /api/batches/{id}`                  | 批次详情、组件判定、抽样与状态时间线             |
| 摄入 | `POST /api/intake`                       | 写入检验行并运行主工作流至确认点               |
| 摄入 | `POST /api/intake/{task_id}/confirm`     | 人工确认或拒绝后恢复工作流                  |
| 判定 | `POST /api/batches/{id}/judge`           | 独立重跑批量判定，未确认 SN 返回清单           |
| 异常 | `POST /api/incidents`                    | 创建异常                           |
| 异常 | `GET /api/incidents`                     | 异常列表                           |
| 异常 | `GET /api/incidents/{id}`                | 异常详情                           |
| 异常 | `POST /api/incidents/{id}/assign`        | 指派责任人与时限                       |
| 异常 | `POST /api/incidents/{id}/capa`          | 记录 CAPA 与验证状态                  |
| 复检 | `POST /api/incidents/{id}/reinspections` | 写入复检记录（不复用初检参数）                |
| 复检 | `GET /api/incidents/{id}/reinspections`  | 查看复检记录                         |
| 放行 | `POST /api/batches/{id}/release`         | 运行七项断言，成功则写放行决定                |
| 报告 | `POST /api/batches/{id}/report`          | 生成版本化报告                        |
| 报告 | `GET /api/batches/{id}/reports`          | 报告列表                           |
| 报告 | `GET /api/batches/{id}/reports/{rid}`    | 单份报告内容                         |
| 规则 | `GET /api/quality-rule-versions`         | 查询可选用规则版本                      |
| 轨迹 | `GET /api/batches/{id}/traces`           | 按时间顺序读取任务轨迹                    |

### 7.1 错误约定

| 状态码 | 语义                             |
| --- | ------------------------------ |
| 400 | 请求数据不合法、规则版本未知、SN 跨批次冲突        |
| 404 | 批次/异常 ID 不存在                   |
| 409 | 状态冲突（当前状态不允许该操作、批次已归档、报告类型不匹配） |
| 500 | 服务端内部错误                        |

错误体统一为 `{"detail": ...}`，对象形式的 detail 会带上`reason` 字段说明具体原因。


### 7.2 前端工作台

`app/static/` 提供 10 个页面，**无构建链**：直接是原生 HTML + JavaScript，由 FastAPI 挂载在 `/static`，`GET /` 302 跳转到 `/static/index.html`。

| 页面               | 职责                           |
| ---------------- | ---------------------------- |
| `index.html`     | 工作台：批次列表、规则版本下拉、创建批次、按 ID 进入 |
| `intake.html`    | 第 1 段：送检与人工确认                |
| `batch.html`     | 第 2 段：详情、判定、发起异常             |
| `incidents.html` | 全局异常列表                       |
| `incident.html`  | 异常详情：指派、CAPA                 |
| `recheck.html`   | 第 4 段：创建复检记录、查看复检历史          |
| `release.html`   | 放行断言执行                       |
| `report.html`    | 报告生成与查看                      |
| `trace.html`     | Agent 任务轨迹时间线                |
| `state.html`     | 静态参考页：状态转移表、断言清单、判定引擎说明      |

前端三条硬约束：**零构建**（无 package.json / vite / webpack）、**零 CDN**（全部本地相对资源）、**零mock**（后端未提供的能力显式标注，不造假数据）。每个页面均实现加载/成功/失败三态，错误信息逐条显示。

## 8. 可追溯性与审计

同一业务动作通过三类记录建立审计链：

| 记录类型     | 内容                                                           |
| -------- | ------------------------------------------------------------ |
| **规则快照** | 每条inspection 行保存判定时的完整规则内容，规则变更不影响历史结论                       |
| **证据引用** | 结论 → evidence 表 → 原始文件，链路完整                                  |
| **任务轨迹** | 每个 Agent 任务的 skill 名、输入引用、插件调用、参数摘要、模型版本、验证结果、失败原因、人工动作、开始时间 |

轨迹字段覆盖了可复演的五个问题：**模型输出什么、系统调用了什么、验证结果如何、谁做的操作、什么时候发生的**（对应 `trace.html` 的五问展示）。

## 9. 实现现状与演进路径

本节说明各能力当前所处的阶段，以及从当前形态走向完整形态的路径。

### 9.1 主链与异常子图的编排关系

主工作流（LangGraph）当前承载数据入场、抽取、人工确认、判定、抽样与状态推进。异常子图尚未挂入主工作流，**异常闭环目前由 API 分段驱动**：`assign` / `capa` / `reinspections` 三个接口各自独立推进异常状态，通过状态机规则保证顺序合法。

这是有意的分步设计：异常闭环涉及人工长时间介入（责任认定、整改措施、复检排期），不适合塞进一个同步工作流。演进方向是把异常子图接入主工作流，用 checkpointer 承载跨时间的暂停与恢复。

### 9.2 AI 归因的调用方式

AI 归因的触发与人工采纳接口**已实现**（2026-10-13 更新）：`POST /api/incidents/{id}/attribute`（`app/api/incidents.py`）支持触发归因与三态决策（采纳/驳回/搁置），仅采纳写入确认根因；结构化假设 + 证据存在性门禁已落地（`app/plugins/attribution.py`）。

尚未实现的 P0 部分（2026-10-14 审计确认）：FR-3.1 关系视图（物料批号/设备/时间窗口关联）、FR-3.3 缺失证据清单输出、FR-3.4 影响范围计算（待调查 SN 集合）。`cross_batch_counts` 参数存在但 API 侧未传入。

### 9.3 模型客户端的运行配置

平台定义了 LLM 客户端抽象，默认实现是 `MockLLMClient`，使用固定fixture 响应，保证测试与离线环境可复现。**真实模型客户端已接入运行配置**（2026-10-13 更新）：设置 `ZHL_LLM_API_KEY`（可选 `ZHL_LLM_BASE_URL` / `ZHL_LLM_MODEL`）即自动切换 OpenAICompatClient（`app/main.py`）；未配置时保持 Mock，测试零网络。

### 9.5 人工拒绝交付的落地方式

**已实现**（2026-10-13 更新）：`POST /api/batches/{id}/reject`（`app/api/release.py`），请求体需 `rejected_by`、`reason`；同事务生成异常处置报告并自动归档。状态机与守卫就位。

### 9.6 规则版本的管理能力

规则版本当前以**查询接口**（`GET /api/quality-rule-versions`）对外提供，供前端下拉选择；管理面（创建、发布、停用）属于下一阶段的建设内容。支撑管理面的关键约束**已在数据库层就位**：已发布的规则版本通过触发器禁止修改，这是管理面落地时的安全基础。

配套的 `scripts/seed-demo.ps1` 提供幂等种子数据，把演示规则版本置为 `published` 状态，保证下拉里有可用选项。

### 9.7 报告的数据引用深度

报告生成能力已就位，支持 Markdown 与结构化 JSON 双格式，按「批次+类型+版本」保存且历史不覆盖。当前报告内容主要基于输入数据组织，**尚未完整引用真实判定统计与实际放行断言结果**。

### 9.8 闭环与异常自动化的缺口（2026-10-14 审计确认；前两项已修复）

对照功能需求文档的 P0 审计确认三项缺口，修复计划见 `docs/superpowers/plans/2026-10-14-p0-closure-fixes.md`：

1. ~~**复检通过后的闭环流转缺失**~~ **已修复（2026-10-14）**：新增 `POST /api/incidents/{id}/close`——五条件校验（domain `close_incident`）→ 异常 `pending_recheck → closed`；批次全部异常终态时同事务转 `pending_release`。关闭为质量工程师的最终签署动作，复检通过不自动关闭；capa 端点扩展支持待复检态补勾"已验证"。验收样例三 e2e 已改走 close API（`tests/e2e/test_closure.py` + `test_sample3_incident_closure.py`）。
2. ~~**异常事件不自动创建**~~ **已修复（2026-10-14）**：`app/plugins/auto_incident.py::ensure_incident`（幂等）接入主链 `batch_transition`（判定 Fail→rule_fail / 抽样 Fail→sample_fail / 规则缺失→rule_missing，同事务）与 intake 跨批次冲突路径（data_consistency，severity=critical，挂被占用批次）。

### 9.9 报告类型约束与内容深度（随 §9.7 一并跟踪）

未放行批次（`pending_judge`/`isolated` 等）当前仍可生成「放行报告」（`app/api/reports.py` 仅约束 rejected 批次），且放行报告中断言结果为渲染层占位（`app/skills/report_skill.py`）。修复随闭环缺口一并排期。

## 10. 验证策略

| 层次        | 手段                         | 说明                              |
| --------- | -------------------------- | ------------------------------- |
| **领域层**   | 纯函数单测                      | 判定、抽样、状态机、放行断言脱离数据库与模型独立测试      |
| **API 层** | TestClient + SQLite 内存库    | 注入 session factory，无需PostgreSQL |
| **契约层**   | 46 个 API 冒烟测试              | 覆盖全部路由与三态错误路径                   |
| **真实环境**  | PostgreSQL 容器 + uvicorn 实起 | 验证触发器、排他约束、事务边界与静态托管            |
| **前端**    | node + DOM 桩逐页执行           | 验证内联脚本无未定义符号、无语法错               |
| **构建约束**  | 关键词与文件扫描                   | 确认零框架、零 CDN、无构建产物               |

测试环境的会话注入是关键约定：每个 app factory 用自己的 session factory 注入，确保测试读写的都是内存库，不会串到真实数据库。

**已知陷阱**：验证路由是否存在**不要遍历 `app.routes`**——新版 FastAPI 把 `include_router` 的结果存为懒加载对象，`path`/`methods` 均为 `None`，遍历会得到 0 条并误判。应使用 TestClient 打真实请求或读 `/openapi.json`。

## 11. 运行配置与常用命令

### 11.1 环境变量

| 配置                                                       | 用途                                   |
| -------------------------------------------------------- | ------------------------------------ |
| `ZHL_DATABASE_URL`                                       | PostgreSQL 连接串，生产应用与 Checkpointer 共用 |
| `ZHL_EVIDENCE_ROOT`                                      | 证据文件根目录，默认项目内 `data/evidence`        |
| `ZHL_LLM_API_KEY` / `ZHL_LLM_BASE_URL` / `ZHL_LLM_MODEL` | 真实 LLM 客户端配置（已预留，见 §9.3）             |

未配置 `ZHL_DATABASE_URL` 时应用**拒绝启动**，不静默回退到空 SQLite——避免空库造成的全量 404 掩盖真实配置问题。

### 11.2 常用命令

| 目的       | 命令                                                 |
| -------- | -------------------------------------------------- |
| 启动数据库    | `.\scripts\start-pg.ps1`                           |
| 写入演示规则版本 | `.\scripts\seed-demo.ps1`                          |
| 启动应用     | `.\scripts\restart-app.ps1 -AutoPort`              |
| 全量测试     | `.venv\Scripts\python.exe -m pytest tests`         |
| 代码检查     | `.venv\Scripts\python.exe -m ruff check app tests` |

### 11.3 前端与接口

| 地址                                          | 说明              |
| ------------------------------------------- | --------------- |
| `http://127.0.0.1:<port>/`                  | 302 跳转至工作台      |
| `http://127.0.0.1:<port>/static/index.html` | 工作台首页           |
| `http://127.0.0.1:<port>/docs`              | 接口文档（可核对待挂载的路由） |

`restart-app.ps1` 的 `-AutoPort` 参数会在端口被占时自动顺延到下一个空闲端口。

### 11.4 运维注意事项

| 现象                                                           | 判断                     | 处理                    |
| ------------------------------------------------------------ | ---------------------- | --------------------- |
| 接口 404/405，且 `/docs` 里没有对应路由                                 | 进程未加载最新代码              | 重启服务，确认带 `--reload`   |
| `netstat` 报 LISTENING，但 `tasklist` 查不到该 PID                  | 已死进程的幽灵 socket         | 换端口（`-AutoPort`）或重启系统 |
| 日志出现 `/.well-known/appspecific/com.chrome.devtools.json` 404 | Chrome DevTools 探测，可忽略 | 无需处理                  |
| 日志里同一页面反复加载                                                  | 页面在自动重载，检查前端循环或浏览器扩展   | 关闭 DevTools 后观察       |

服务无鉴权，`release`、`report` 等写接口能改变业务状态，**必须限制在本机（`127.0.0.1`），不可对外暴露**。`restart-app.ps1` 已内置该守卫，传非本机地址会拒绝启动。
