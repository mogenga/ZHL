## 1. 架构目标与约束

### 1.1 架构必须满足的五条

| 目标     | 架构含义                       |
| ------ | -------------------------- |
| 判定可复算  | 每次判定保存规则快照，历史结论不被后续规则变更改写  |
| 状态流转确定 | 状态转移是纯函数，模型无法改写            |
| 证据可回溯  | 任何结论都能追到原始文件与任务轨迹          |
| 过程可复演  | 每个 Agent 任务的输入、调用、输出、验证全留痕 |
| 约束下沉  | 唯一性、完整性、不可变性由数据库声明式约束保证，不依赖应用层校验 |

---

## 2. 分层架构

```text
┌─ 接入层    FastAPI 单进程，提供 API 与内置页面
├─ 编排层    AGH Skill 五段编排，唯一流程入口，记录任务轨迹
├─ 能力层    模型作用于：抽取与置信度 · 证据化归因 · 规则阈值推荐
│            纯函数负责：判定计算 · 抽样查表 · 状态流转 · 放行断言
├─ 治理层    证据库 · 任务轨迹 · 报告生成 · 操作留痕
└─ 数据层    PostgreSQL，声明式约束 + JSONB + 行级锁，快照与判定证据以 JSONB 存储
```

### 2.1 各层职责

| 层   | 职责                              | 不负责           |
| --- | ------------------------------- | ------------- |
| 接入层 | 接收文件与操作请求，渲染批次、隔离清单、判定详情、断言阻断界面 | 业务判断          |
| 编排层 | 按五段主链调度 Skill 与 Plugin，保存任务轨迹   | 直接改状态、直接写判定结论 |
| 能力层 | 调用模型做非确定性判断，调用纯函数做确定性计算         | 状态流转决策        |
| 治理层 | 证据落库、轨迹记录、报告生成、操作留痕             | 业务判断          |
| 数据层 | 事务、唯一约束、外键完整性                   | 业务语义          |

### 2.2 为什么编排层只有一层

编排层不拆分，理由是主链已收敛为五段，且每段之间存在强顺序依赖。引入多编排器会带来事务边界不清与轨迹分散，得不偿失。段内的并行（例如多组件同时判定）由能力层内部用批量接口解决，不上升为编排层。

## 3. AGH 与业务逻辑的边界

这是整个架构最需要防守的位置。

### 3.1 错误做法与正确做法

| 做法 | 模型的角色            | 后果                        |
| -- | ---------------- | ------------------------- |
| 错误 | 模型决定调用顺序，也决定状态转移 | 同一批数据两次运行可能得到不同状态，闭环不再可复现 |
| 正确 | 模型只能提交转移请求与理由    | 转移是否合法由状态机判定，可复现          |

### 3.2 状态流转的实现约束

状态转移表与前置条件写死在 Plugin 内部，对外暴露的接口只有两个语义：

```text
transition(batchId, fromState, toState, reason, operator) → Accepted | Rejected
```

返回 `Rejected` 时必须给出不满足的前置条件。模型拿到的就是这个结果，无法绕过。

**模型可以提交的**：目标状态、理由、关联证据。

**模型不能做的**：跳过前置条件、直接改写状态、修改转移表。

### 3.3 Skill 与 Plugin 划分

| 组件                    | 类型     | 职责               | 不负责        |
| --------------------- | ------ | ---------------- | ---------- |
| Intake Skill          | Skill  | 识别文件、补齐字段、提出确认任务 | 直接放行       |
| Decision Skill        | Skill  | 编排并解释规则计算        | 修改规则值      |
| TraceCAPA Skill       | Skill  | 汇集证据、提出归因假设与建议   | 确认根因、关闭异常  |
| RuleAdvisory Skill    | Skill  | 基于历史数据推荐规则参数     | 直接发布规则     |
| Report Skill          | Skill  | 汇总事实、生成报告草稿      | 编造数据、改变状态  |
| InspectionData Plugin | Plugin | 读取 CSV 与质检单文件    | 业务判定       |
| RuleEngine Plugin     | Plugin | 确定性公式计算与规则快照     | 模型推理       |
| Sampling Plugin       | Plugin | ISO 表查询、样本冻结、统计  | 任意生成 AQL   |
| Traceability Plugin   | Plugin | SN、批次、物料、设备关系查询  | 主观归因       |
| StateMachine Plugin   | Plugin | 状态转移校验与落库        | 接受非法转移     |
| ReleaseGate Plugin    | Plugin | 放行断言与证据核对        | 放行未满足断言的批次 |
| EvidenceStore Plugin  | Plugin | 保存源文件、证据与轨迹      | 决定放行       |

**规律**：凡涉及计算的走 Plugin 且无模型，凡涉及理解与组织的走 Skill 且必须调用 Plugin。Skill 永远不能绕过 Plugin 直连数据库。

## 4. 数据架构

### 4.1 表清单

```text
rule_versions规则版本，发布后不可改
delivery_batches             交付批次
module_inspections           组件检验记录，含规则快照与判定证据
quality_incidents            异常事件
incident_sn_links            异常与 SN 的关联关系
reinspections                复检记录
samples                      抽样轮次与样本清单
sample_conclusions           抽样结论，n 与 AC 与 RE
evidence                     证据库
agent_task_traces            Agent 任务轨迹
reports                      报告版本
```

### 4.2 关键约束

| 约束 | 实现方式 | 防的是什么 |
| --- | --- | --- |
| 组件在批次内唯一 | `UNIQUE(batch_id, sn)` | SN 重复 |
| SN 不可跨批次 | 复合外键 + `EXCLUDE` 排他约束 | 数据冲突被静默覆盖 |
| 异常必须关联 SN | `incident_sn_links` 外键强制，不用自由文本 | 影响范围算不出来 |
| 规则版本发布后不可改 | 声明式权限 + 触发器双重保障 | 历史结论被改写 |
| 原始检验值不可改 | 列级权限 + 触发器双重保障 | 证据被篡改 |
| 抽样结论唯一 | `UNIQUE(batch_id, inspection_type, rule_version_id, sample_round)` | 跨批次覆盖 |
| 证据只追加 | 撤销 UPDATE 与 DELETE 权限 | 证据链断链 |

**这些约束落在数据库层，不只靠应用层校验。** 应用层存在并发窗口，约束下沉到数据库才是唯一可靠方式。

**以声明式约束为主，触发器为辅**。PostgreSQL 的唯一约束、外键、`CHECK`、排他约束是引擎原生能力，执行计划可见、性能稳定，因此能用声明式表达的都不写触发器。触发器只用于「权限回收」与「版本不可变」这两类无法声明式表达的语义。

### 4.3 快照存储

规则快照与判定证据使用 `JSONB` 类型存储。

理由是 JSONB 相比文本有两项实质优势：可建立 GIN 索引，支持按判定项、失败原因、假设类别做结构化查询；支持 `@>` 包含运算，可直接查询「某类判定的全部记录」。这使归因回测与判定分布统计不必回表解析。

关键计算项另设独立列冗余，保证常用查询不触碰 JSONB。

### 4.4 并发与隔离

批量判定会对同批次的多行记录连续写入。PostgreSQL 的行级锁与 MVCC 允许读不阻塞写、写不阻塞读，不会让整批次判定被单个事务长时间锁住。

默认隔离级别为 `READ COMMITTED`；放行与状态转移这类强一致场景提升为 `REPEATABLE READ`，确保断言检查所依据的数据在整个事务内不变。

### 4.5 事务边界

| 操作     | 事务范围                  |
| ------ | --------------------- |
| 摄入一批组件 | 单事务内写全部记录与证据，任一失败整批回滚 |
| 判定一个批次 | 单事务内写全部组件判定、抽样结论、批次状态 |
| 状态转移   | 单事务内校验前置条件并更新状态，写轨迹   |
| 放行     | 单事务内执行断言、写放行证据、更新状态   |
| 报告生成   | 单事务内写报告版本与快照引用        |

**不允许跨事务的部分**：任何涉及模型调用的步骤。模型调用在事务外完成，拿到结构化结果后再开事务落库。理由是模型调用耗时长，长事务会持有连接并累积行级锁，拖长同批次其他写入的等待时间。

## 5. 确定性核心设计

### 5.1 判定引擎

```python
def judge(inspection, rule_snapshot) -> Decision:
    """纯函数。同样的输入必然得到同样的输出。"""
    checks = [
        check_required_fields(inspection),
        check_power_range(inspection, rule_snapshot),
        check_parameter_tolerances(inspection, rule_snapshot),
        check_current_band(inspection, rule_snapshot),
        check_appearance(inspection),
    ]
    return Decision(
        result=Pass if all(c.passed for c in checks) else Fail,
        checks=checks,
        rule_snapshot=rule_snapshot,
    )
```

**约束**：不读数据库、不取当前时间、不调用随机数、不调用模型。四项全部违反都会破坏可复算性。

### 5.2 容差公式

```text
lower = 标准值 × (1 − 容差%)
upper = 标准值 × (1 + 容差%)
lower ≤ 实测值 ≤ upper        闭区间
```

浮点比较统一用容差区间判断，避免精度问题导致边界值误判。等于上下限均判 Pass。

### 5.3 放行断言

```python
def assert_release(batch_id) -> AssertionResult:
    """逐条返回，不可只返回布尔值。"""
    checks = [
        check_state(batch_id, "待放行"),
        check_sample_passed(batch_id),
        check_no_open_critical_incident(batch_id),
        check_no_isolated_sn(batch_id),
        check_all_evidence_present(batch_id),
        check_all_capa_verified(batch_id),
    ]
    return AssertionResult(
        passed=all(c.passed for c in checks),
        checks=checks,          # 逐条结果，供界面展示
    )
```

**必须逐条返回而不是返回一个布尔值。** 放行被拦截时，用户必须知道缺哪一条。若只返回 False，界面无法给出可执行的提示，断言就失去了意义。

### 5.4 状态转移表

```text
draft        → pending_intake
pending_intake → pending_judge
pending_judge→ pending_release   条件：全部组件 Pass 且抽样 Pass
pending_judge    → isolated      条件：任一组件 Fail 或抽样 Fail 或数据冲突或规则缺失
isolated         → disposing      条件：已指定责任人与时限
disposing        → pending_recheck 条件：临时措施与纠正措施已确认
pending_recheck  → pending_release 条件：全部严重异常复检通过且措施有效
pending_recheck  → rejected         条件：复检失败
pending_release  → released        条件：断言全通过且人工批准
任意非归档       → rejected         条件：人工拒绝交付
```

转移表以数据形式定义，但**不可由模型修改**。启动时加载并校验，配置非法则拒绝启动。

## 6. AI 能力设计

### 6.1 三处落点的实现约束

| 落点     | 模型输出             | 强制约束                    |
| ------ | ---------------- | ----------------------- |
| 抽取与置信度 | 结构化字段加字段级置信度     | 低置信字段必须进人工确认，不得自动入库     |
| 证据化归因  | 假设数组，每条含证据引用与置信度 | 证据 ID 必须真实存在，否则判定为幻觉并拒绝 |
| 规则阈值推荐 | 建议值加推导依据         | 依据中的样本量与覆盖率必须可查，不得编造    |

### 6.2 幻觉防护

归因假设的每条证据引用都要做存在性校验：

```text
模型给出 evidence: ["inspection:IM-102", "materialLot:M-2026-01"]
     ↓逐条查询
inspection:IM-102不存在 → 标记幻觉
materialLot:M-2026-01 不存在 → 标记幻觉
     ↓
幻觉比例超阈值 → 拒绝整个输出，返回证据不足
```

**不做这一步，结构化输出只是形式上的可信。** 模型总能编出格式正确但不存在的 ID。

### 6.3 提示词与解析

三处落点的输出都用 JSON Schema 约束，解析失败时的处理是明确的：

| 情况        | 处理                  |
| --------- | ------------------- |
| JSON 解析失败 | 重试一次，仍失败则转人工并记录失败轨迹 |
| 必填字段缺失    | 转人工，不猜测补齐           |
| 证据引用不存在   | 标记幻觉，比例超阈值则拒绝输出     |
| 置信度缺失或超界  | 视为低置信，转人工           |

**不允许静默降级为默认值。** 任何兜底都必须产生异常记录。

### 6.4 模型不可用时

模型服务不可用时，系统仍须支持人工完成全链路：判定走同一套RuleEngine Plugin，归因转人工填写，报告基于结构化数据生成。任务轨迹须记录失败原因，不留空白。

## 7. 证据与可复演设计

### 7.1 证据类型

| 类型   | 内容                       | 存放             |
| ---- | ------------------------ | -------------- |
| 原始文件 | 质检单图像、IV 设备 CSV          | 文件目录 + 证据表记录哈希 |
| 抽取结果 | JSON、模型版本、字段置信度          | 证据表            |
| 人工确认 | 确认人、确认时间、修改差异            | 证据表            |
| 判定快照 | 规则快照、逐项结果、公式             | 记录表字段          |
| 任务轨迹 | 输入、Skill、Plugin、参数、输出、验证 | 轨迹表            |
| 报告快照 | 报告版本、源快照引用               | 报告表            |

### 7.2 可复演要求

任一结论可完整回答五个问题：

```text
模型提出了什么
系统调用了什么
哪条规则通过或失败
谁作出了最终决定
依据的原始数据是什么
```

这五问对应的字段全部落库，不依赖日志文件。日志是调试用的，证据表才是审计依据。

### 7.3 哈希与完整性

原始文件入库时计算内容哈希并入库。证据被替换时哈希不匹配，校验会发现。这个机制不防止篡改，但能让篡改被发现。

## 8. 技术栈与代码组织

### 8.1 技术栈

| 层   | 选型                       | 理由                                |
| --- | ------------------------ | --------------------------------- |
| 语言  | Python 3.11+             | AGH 生态原生支持                        |
| Web | FastAPI + 内置静态页          | 单进程同时提供 API 与页面，零构建               |
| 数据  | PostgreSQL 15+           | 声明式约束、JSONB、排他约束、行级锁直接对应架构要求      |
| ORM | SQLAlchemy 2.0           | 显式事务边界，映射层与数据库解耦                |
| 校验  | Pydantic v2              | 结构化输出的 Schema 约束                  |
| 调度  | AGH Skill                | 编排层的实际执行者                         |

不引入前端构建链，不引入 Redis，不引入消息队列。单进程能跑通的系统不要拆成多服务。

### 8.2 代码分层依赖

代码按接入层、编排层、能力层、治理层、数据层分包组织，目录结构在开发过程中按实际情况调整，不作为约束。

**唯一固定的是依赖方向**：domain 层不依赖 infra 层。判定与断言是纯函数，不读库、不取当前时间、不调模型，因此可以脱离数据库与模型独立测试。Skill 与 Plugin 只做编排与 IO。

### 8.3 测试策略

| 层       | 测试方式         | 关注点               |
| ------- | ------------ | ----------------- |
| domain  | 纯函数单元测试      | 边界值、闭区间、状态转移的非法路径 |
| plugins | 集成测试         | 约束是否生效、事务是否回滚     |
| skills  | 用固定模型输出做回放测试 | 结构化输出解析、幻觉拒绝      |
| 端到端     | 四组验收样例       | 全链路可复现            |

**domain 层测试不依赖数据库与模型**，跑得快，是回归的主要防线。

## 9. 关键接口

### 9.1 Plugin 契约

```python
class Plugin(Protocol):
    def name(self) -> str: ...
    def health_check(self) -> HealthStatus: ...
    def invoke(self, payload: dict, ctx: TaskContext) -> PluginResult: ...
```

`TaskContext` 携带 taskId、证据写入器、操作人。**Plugin 不自行写库**，通过 ctx 写入，便于统一留痕。

### 9.2 核心接口

```text
POST /api/intake                  上传文件，启动摄入，返回 taskId
GET  /api/tasks/{taskId}          查询任务状态与轨迹
POST /api/batches/{id}/judge      触发判定
GET  /api/batches/{id}            批次详情含判定证据
POST /api/incidents/{id}/hypotheses  触发归因
POST /api/incidents/{id}/adopt    人工采纳假设
POST /api/batches/{id}/recheck    创建复检
POST /api/batches/{id}/release    尝试放行，返回逐条断言
GET  /api/batches/{id}/report     获取报告
GET  /api/evidence/{id}           获取证据内容
```

**放行接口必须返回逐条断言结果**，即使通过也要返回全部检查项，供界面展示与留痕。

## 10. 失败模式与降级

| 异常             | 处理                                                  | 是否降级 |
| ---------------- | ----------------------------------------------------- | -------- |
| OCR 置信度低     | 转待人工确认                                          | 否       |
| 文件解析失败     | 保留源文件与失败轨迹，创建重新提交任务                | 否       |
| SN 重复或跨批次  | 创建数据一致性异常，阻断两个批次                      | 否       |
| 型号无已发布规则 | 状态为规则缺失，禁止猜测阈值                          | 否       |
| ISO 参数无映射   | 抽样判为规则异常，不得按默认值放行                    | 否       |
| 溯源证据不足     | 输出缺失证据清单，不输出唯一根因                      | 否       |
| 归因输出幻觉超标 | 拒绝输出，转人工                                      | 否       |
| 模型服务不可用   | 人工使用同一 RuleEngine Plugin 完成判定，记录失败原因 | 是       |
| 约束校验失败     | 事务回滚，返回冲突明细，不做自动合并                  | 否       |
| 数据库连接中断   | 事务重试三次后失败退出，重启后从状态机当前态续跑      | 是       |

**原则**：只有「模型服务不可用」与「数据库连接中断」两处允许降级，且降级后系统仍须给出完整结论。**其余一律阻断，不允许默认值放行。**
